# AI 위임 루프 v1.3 실전 매뉴얼

**목표:** 반복 업무 하나를 인터뷰로 문서화하고, 재사용할 도구와 실패 가능한 검증을 쌓아 다음 실행의 설명량과 재작업을 줄인다.

이 절차는 원문 가이드의 프로세스·툴박스·증명·개선 루프와 네 개 프롬프트를 실무용으로 정리했다. 보안·승인 경계, 객관적 검증 등급, Git 검토 절차를 보완했다. 아직 특정 팀이나 업무에 적용해 검증한 결과는 아니다.

## 1. 어떤 일을 고를까

후보 업무가 아래 세 조건을 모두 만족해야 한다.

1. 주 1회 이상 반복한다.
2. 나쁜 결과를 구체적인 기준으로 알아본다.
3. 새 직원에게 20분 안에 설명할 수 있다.

가장 복잡한 일부터 시작하지 않는다. 주간 고객 업데이트, 주간 보고, 반복 메일처럼 입력과 결과가 고정된 업무가 시작점이 되기 쉽다.

다음 업무는 먼저 범위를 줄이거나 보류한다.

- 매번 판단 기준이 크게 달라져 규칙을 적을 수 없는 업무
- 맞고 틀림을 외부 자료나 명시적 기준으로 판정할 수 없는 업무
- 비밀번호·API 키·토큰을 저장해야만 수행할 수 있는 업무
- 채용, 금융, 법률, 의료 등 사람의 권리나 큰 손실에 영향을 주는 업무를 사람 검토 없이 자동 결정하려는 경우

민감한 업무는 보조 초안이나 검토 목록 생성으로 한정하고, 최종 판단은 권한 있는 사람이 한다.

## 2. 먼저 저장 위치와 권한을 정한다

매뉴얼은 채팅 기록이 아니라 업무 폴더에 둔다. 파일을 읽고 쓸 수 있는 에이전트라면 실제 마스터 폴더에서 작업한다.

Grok·ChatGPT(Codex)·Claude의 네이티브 설치는 [도구별 설치 안내](installation.ko.md)를 따른다. 스킬 설치와 업무 파일 쓰기 권한은 별개다.

파일을 직접 갱신할 수 없는 도구에서는 로컬 컴퓨터나 승인된 드라이브에 마스터를 하나 둔다. Project에 사본으로 업로드한 파일은 새 내용을 마스터에 저장한 다음 기존 사본을 교체한다. 같은 문서의 낡은 버전을 함께 두지 않는다. 일반 업로드 사본은 원본 수정만으로 갱신되지 않는다. 연결된 자료의 실시간 동기화 여부는 해당 연결 방식에서 확인한다.

에이전트가 실제 파일을 쓰지 못하면 저장한 척하지 않는다. 파일 전체 내용, 정확한 경로, 사람이 수행할 저장·교체 단계를 제시한다.

## 3. 업무 폴더를 만든다

업무 하나에 폴더 하나를 둔다.

```text
[job-name]/
  SKILL.md
  files/
    INDEX.md
    [재사용 도구와 참조 자료]
  examples/
    [통과하고 승인된 완성본만]
  notes.md
```

- `SKILL.md`에는 목적, 실제 입력할 문장, 입력과 위치, 산출물 계약, 수행 순서, 결정 규칙, 완료의 정의, 예외를 기록한다. 산출물 계약은 독자·사용 목적·톤·형식·길이·필수 범위·제외 범위·저장 위치의 확인된 답변이다. 미정 값은 UNVERIFIED와 필요한 입력으로 남기고 추측하지 않는다.
- `files/INDEX.md`에는 파일명·용도·저장일을 한 줄씩 기록한다.
- `files/`에는 재사용 도구만 둔다. 도구 파일명은 안정적으로 유지하고 날짜나 버전 번호를 넣지 않는다.
- `examples/`에는 기준을 통과하고 개인정보·비밀정보를 제거한 완성본만 둔다. 가상의 예시는 실제 통과 사례처럼 표시하지 않는다.
- `notes.md`는 최신 변경이 위에 오도록 오류 원인과 수정, 재검증 결과를 기록한다.
- 업무가 바뀌어 서로 다른 트리거를 요구하면 폴더를 분리한다. 혼합된 업무는 먼저 각 매뉴얼의 실제 호출 문장을 분명히 한다.

### 툴박스에 저장할 것

1. 숫자 추출, 파일명 정리, 형식 변환 같은 기계적 단계의 스크립트
2. 업무별 값을 대괄호 자리표시자로 바꾼 템플릿
3. 최신 상태와 사용 권한을 확인한 참조 데이터
4. 담당자가 통과를 확인한 완성 예시
5. 브랜드 음성, 출력 형식, 금지 표현 같은 규칙 파일
6. 자주 쓰는 하위 단계용 저장 프롬프트

일회성 산출물, 미승인 초안, 자격 증명은 저장하지 않는다. 개인정보·고객 자료는 보존 근거와 접근 권한을 확인하고 필요한 최소량만 둔다. 두 파일이 같은 용도라면 최신 원본을 확인한 후 하나만 남긴다. 삭제 전에 참조 위치, 복구 방법, 담당자 승인을 확인한다.

## 4. 첫 매뉴얼을 30분 안에 세운다

첫 30분은 목표 시간이지 성공을 보장하는 수치는 아니다.

1. 업무를 한 줄로 적는다. 예: “매주 월요일 광고 대시보드의 지난주 수치로 고객 업데이트를 쓴다.”
2. [프롬프트 1](prompts/01-interview.md)로 인터뷰한다. 질문은 한 번에 하나씩 하고 최소 8개를 묻는다. 답변은 실제 사례를 포함한 완전한 문장으로 한다. 인터뷰 완료 전에는 SKILL 파일을 만들지 않는다.
3. 나온 매뉴얼에서 잘못 적힌 내용과 빠진 판단을 직접 바로잡는다. 첫 버전은 초안이다. 실제 호출 문장은 사용자가 업무를 시킬 때 입력할 말 그대로 쓴다.
4. 매뉴얼을 따라 첫 실행을 한다. 입력 자료의 최신성·권한을 확인하고, 결과를 검토한다.
5. 결과가 실제 기준을 통과한 뒤 [프롬프트 2](prompts/02-toolbox.md)로 반복 가능한 부분을 저장한다. 상황 특화 값은 자리표시자로 바꾼다.
6. [프롬프트 3](prompts/03-proof.md)으로 검증 5~10개와 매 실행의 보고·중단·승인 규칙을 업무 `SKILL.md`에 저장한다. 항목마다 실제로 실패할 수 있고, 다른 사람이 확인할 수 있는 근거가 있어야 한다. 툴박스 저장 단계에서는 재실행하지 않는다.
7. 검증 항목과 실행 규칙을 저장하고 사람이 확인한 뒤 동일한 종류의 업무를 두 번째 실행한다. 저장한 파일이 실제로 사용됐는지, 설명이 줄었는지, 새로 만든 것이 무엇인지 기록한다. 메일·게시·삭제·결제·배포·계정·권한 변경에는 이번 재실행에 대한 별도 명시 승인이 필요하다.
8. 잘못된 결과가 있으면 채팅 수정만으로 끝내지 않는다. [프롬프트 4](prompts/04-failure-loop.md)로 고친다.

## 5. 증거로 완료를 판정한다

“좋다”, “전문적이다”, “명확하다”는 단독 검증 항목이 아니다. 다음처럼 검증자가 독립적으로 확인할 수 있는 증거를 고른다.

- 원본 파일 경로·시트·행까지 추적되는 수치
- 실제 열리는 링크와 확인 시각
- 렌더링한 화면이나 문서의 캡처
- 실행된 테스트와 종료 결과
- 원문 인용 또는 전사와 대조한 주장
- 단어 수·레코드 수·필수 항목 수
- 승인된 기준 파일의 표기와 일치 여부

### 검증 등급

해당 업무에 실제로 적용한 가장 높은 등급과 근거를 보고한다. 등급은 순위를 보이기 위한 공통 기준이며, 모든 결과물이 반드시 L4여야 한다는 뜻은 아니다.

| 등급 | 확인한 범위 | 근거 예시 |
| --- | --- | --- |
| L0 | 확인을 하지 않았거나 증거가 없다 | 생성만 했음. 완료로 보고하지 않고 미검증으로 표시 |
| L1 | 산출물 내부의 구조·형식·개수 | 파일 존재, JSON 파싱, 단어 수, 필수 항목 수 |
| L2 | 원본과 대조한 내용 | 원본 경로/행, 인용문, 기준 파일, 실제 열리는 링크 |
| L3 | 격리된 입력으로 재현 가능한 실행 | 테스트 명령, 합성 fixture, 로그, 재현된 결과 |
| L4 | 실제 시스템에서 읽기 전용으로 확인한 최신 상태 | 확인 대상·범위·시각·조회 근거 |

상태는 `PASS`, `FAIL`, `UNVERIFIED`, `N/A` 중 하나다. 미확인이나 접근 불가를 통과로 간주하지 않는다. `N/A`는 왜 적용되지 않는지 적는다. 한 줄 결과에 항목, 상태, 등급, 증거 위치, 남은 불확실성을 기록한다.

첫 실행에서 세 항목 이상 실패하면 결과 문장을 임시로 고쳐 넘기지 않는다. 실패 레이어를 진단하고 프로세스나 도구를 먼저 고친다. 자격 증명·권한·개인정보·대상 범위와 관련된 항목은 하나라도 실패하면 즉시 중단한다. 수정 후 전체 검증을 다시 돌린다.

외부에 영향을 주는 행동은 검증 등급과 별도의 승인 절차다. 메일 발송, 게시, 결제, 삭제, 배포, 계정·권한 변경 전에는 대상·범위·영향·되돌릴 방법을 명시하고 사용자가 그 행동을 직접 승인해야 한다. 실행 뒤에는 영수증, 작업 ID, 게시 URL 등 실제 결과 증거를 기록한다. 승인이 없으면 초안이나 계획까지만 만든다.

## 6. 실패한 레이어를 고친다

PASS를 만들려고 검증 항목·임계값·기대 결과를 삭제하거나 완화하지 않는다. 기준 오류의 근거가 있으면 원래 결과와 분리 보고하고, 담당자 확인 후 승인된 기준 변경을 기록한다. 예시나 fixture의 정답을 하드코딩하지 않고 업무 규칙을 수정한다. 원래 실패 사례와 다른 비민감 입력을 전체 재검증하고 미실행은 UNVERIFIED로 남긴다.

| 관찰된 오류 | 실패 레이어 | 영구 수정 위치 |
| --- | --- | --- |
| 단계가 빠지거나 순서가 잘못됨, 판단 규칙 누락 | 프로세스 | 업무 `SKILL.md`의 해당 단계·결정 |
| 저장된 파일을 못 찾거나 다시 만들었음, 도구가 낡거나 틀림 | 툴박스 | 해당 파일, 호출 경로, `files/INDEX.md` |
| 잡아야 할 오류를 발견할 검증이 없음 | 증명 | 완료 기준의 검증 항목 |
| 입력 자료·권한·시스템 상태가 바뀌었거나 확인 불가 | 외부 조건 | 최신 근거·접근 권한 확인 또는 담당자에게 인계 |

실패 사실과 근거를 특정하고 원인을 프로세스·툴박스·증명·외부 조건 중 하나 또는 여러 개로 분류한다. 불명확한 원인은 `UNVERIFIED`로 남긴다. 외부 조건 문제를 내부 매뉴얼 결함으로 단정하지 말고 최신 입력·권한·시스템 상태를 확인하거나 담당자에게 넘긴다. 확인된 내부 결함의 위치에 가장 작은 수정만 추가한다. 같은 오류가 두 번째로 반복되면 주의 문구 대신 재발을 막는 규칙을 추가한다. 날짜·오류·모든 원인 레이어·수정·재검증을 `notes.md` 맨 위에 기록한다. 비민감 입력으로 다시 실행해 비교하고, 승인 필요 행동은 이번 재실행에 대한 별도 명시 승인 없이 반복하지 않는다.

## 7. 월간 점검과 Git 기록

월 1회 `files/`, `examples/`, `notes.md`를 확인한다. 쓰지 않는 자료와 중복을 찾아내고, 참조·권한·백업을 확인한 뒤 담당자 승인에 따라 정리한다. 같은 종류의 실패가 notes에 반복되면 프로세스, 툴박스, 증명 중 어느 수정이 실제로 반복되는지 반영한다.

이 매뉴얼을 저장소에서 관리할 때:

1. 현재 브랜치와 작업 트리를 확인한다.
2. 별도 작업 브랜치에서 관련 파일만 수정한다.
3. 검증 결과와 근거를 재현 가능하게 남긴다. 실제로 실행하지 않은 테스트를 성공으로 기록하지 않는다.
4. 변경 내용과 비밀정보 노출 여부를 diff에서 검토한다. 키·토큰, 개인 로그, 임시 산출물은 커밋하지 않는다.
5. 목적, 변경 파일, 검증 결과, 미확인 범위를 적어 PR을 연다.
6. PR 생성은 병합 승인이 아니다. 병합·배포·보호 규칙 변경은 별도 명시 요청이 있을 때 수행한다.

| 콘텐츠 재활용 | 훅/캡션 템플릿, 브랜드 규칙, 허가된 원문·전사 | 주장과 원문 인용 대조, 금지 표현 검색, 길이 제한, 사용 권한 확인 |
| 미수금 안내 | 연체 단계별 승인 문안, 에스컬레이션 규칙, 담당자 연락처 참조 | 금액·기한이 승인된 인보이스와 일치, 결제 링크 확인, 단계와 템플릿 일치 |
| 채용 서류 1차 정리 | 직무 기준, 평가표, 승인된 익명 예시 | 점수마다 지원 자료의 근거, 요약과 원문 모순 검사, 최종 판단은 사람에게 전달 |

## 9. 자주 생기는 실수

- 순서를 인터뷰 전에 직접 작성해 보이지 않는 판단 기준을 놓침
- 여러 업무를 한 폴더에 넣어 서로 다른 규칙이 섞임
- “콘텐츠 도와줘”처럼 너무 넓은 호출 문장으로 스킬을 선택하기 어려움
- 증거 대신 “괜찮아 보인다”는 자기평가를 통과로 취급
- 채팅에서만 고치고 마스터 파일은 갱신하지 않음
- 예시나 참조 파일에 민감한 값·오래된 사본을 남김
- 테스트 계획을 만들고 실제로 실행했다고 표현
