# Skill versions

Plugin release versions and skill interface versions have different scopes.
Neither is an automatic model selection or permission mechanism.

## 2026-10-24 initial version records

`1.0.0` is the first explicit interface version for the owned skills, not their
creation date or a claim of newly added implementation capability. Instructions,
IDs, native coding/RCA calls and verification state remain compatible.
The [Agent Skills metadata field](https://agentskills.io/specification#metadata-field)
allows string-to-string metadata, including a version; top-level `version` is not
introduced as an invented skill field. Strict portable standalone entries keep
their existing frontmatter and display the version in the body instead.

Native plugin `2.0.0` is a breaking package release: the uncleared delegation skill
is removed and new delegation install/ZIP commands refuse distribution. Its old
native call is unavailable; coding/RCA IDs, reviewers, hooks and state v1 stay intact.
The archived third-party skill keeps its own upstream attribution/version; this
project does not assign it a new owned version or license. See [clearance](third-party-clearance.md).

## Updating and checking a version

- Patch: clarification or a compatible correction without changing the supported
  interface. Minor: a compatible capability addition. Major: removal or incompatible
  changes to invocation, required input, output contract or operational obligations.
- Change the owned skill's canonical version when its interface changes, and record
  the actual change and compatibility impact here. Do not renumber unrelated skills.
- Any native payload change also needs an appropriate plugin release version and
  regeneration with `python scripts/build_plugin.py`, followed by `--check`.
- The host caches/updates the plugin as one unit; `metadata.version` is descriptive,
  not a per-skill package manager, automatic migration, dependency resolver or lock.
  Pin an inspected plugin artifact/commit and check the installed SKILL.md bytes
  when an exact version is required. Existing caches need explicit update and a new session.
- Standalone `--check` compares source and installed bytes. Its `.fef-manifest.json`
  `version: 1` is the installation schema, not skill SemVer. Verification state
  `version: 1` likewise remains unchanged. Do not migrate user data just to display a version.

No public release/tag or remote update is implied by an uncommitted version field.
