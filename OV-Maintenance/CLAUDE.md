# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Overview

`OCP-HCK-Score.sh` is a Bash health-check tool for RHOCP (Red Hat OpenShift Container Platform) clusters running OpenShift Virtualization (CNV). It runs fully unattended against a live cluster (`oc login` session) and produces a dated `.txt` report plus a self-contained `.html` dashboard (generated by an embedded python3 heredoc, browser-printable to PDF; python3 is a soft dependency — its absence just skips the HTML output).

`fill_checklist.py` reads that `.txt` report and automatically fills the '점검결과' column of `check_reconstructed.xlsx` (a non-DRM xlsx checklist that mirrors the real corporate `OCP_Virtualization_정기점검_체크리스트.xlsx`, which is DRM-locked and not editable by Claude). Both files live in this repo. `check_reconstructed.xlsx` must only be created/edited on Linux (rhel-prod) — a Windows-side DRM agent silently corrupts xlsx files saved there for openpyxl.

## Running

```bash
./OCP-HCK-Score.sh
```

- Requires an active `oc login` session (`oc whoami` must succeed) and the `oc` CLI on PATH.
- `jq` is optional but improves ClusterOperator verdict accuracy (falls back to raw `oc get co` output otherwise).
- `virtctl` is optional; when absent, VM start/stop/migrate/console checks (5-1/5-2/5-3) are skipped with a warning.
- Disruptive VM tests (5-1 stop/start, 5-2 live migration) are **off by default** to avoid impacting running workloads. Enable explicitly with:
  ```bash
  RUN_VM_DISRUPTIVE=yes ./OCP-HCK-Score.sh
  ```
- Output: `ocp-healthcheck-report-<YYYYMMDD-HHMMSS>-<PID>.txt` (+ matching `.html`) in the current directory, with sections/items numbered to match the xlsx checklist (`1.Cluster구성 / 2.ClusterOperator / 3.API연동 / 4.Network / 5.Virtualization`, 66 items total as of 2026-09-14). The script never assigns pass/fail verdicts itself for most items — either a human fills those into the xlsx from the raw command output, or `fill_checklist.py` does it automatically from the `.txt` report.

## Architecture

The script is a linear sequence of five checklist sections, each populated by a shared logging/report harness:

1. **Report harness** (`write`, `raw`, `section`, `item_header`, `run_cmd`): `write` echoes to both stdout and the report; `raw` writes report-only; `run_cmd` wraps a numbered checklist item, executes the given command, and records success/failure without judging cluster health.
2. **Section 1 — Cluster 구성**: node join/role/version via `oc get nodes`.
3. **Section 2 — ClusterOperator 상태**: iterates a fixed list of 34 known ClusterOperator names, parses `Available`/`Progressing`/`Degraded` conditions per operator (via `jq` if present, always via native `oc get co` for VERSION/SINCE) into a verdict table. Any operator present on the cluster but missing from the fixed list is flagged separately, not silently skipped.
4. **Auto-target discovery** (before section 3): picks a *random* namespace/pod/node/service/PVC/PV/route/VM each run using `rand_line` (uses `shuf` if available, else an `awk`-based fallback) so repeated runs exercise different cluster objects instead of always the same first-listed one. This discovered state (`Q_*` / `V_*` variables) feeds sections 3–5. The Pod-to-Pod ping target (`Q_PEER_IP`/`Q_PEER_NS`, used by 4-2) is selected separately from `Q_NS`, excluding `openshift-*`/`kube-*`/`default` namespaces — those often carry NetworkPolicies that block ICMP by design, which used to cause false-positive failures.
5. **Section 3 — API 연동**: list/describe checks against the auto-discovered namespace/pod/node/service/PV/PVC, plus `oc adm top`, pod log tail (3-10, secret-pattern-masked), a cluster-wide list of PVCs not bound to any Pod/VM (3-6), and a cluster-wide non-Running pod audit distinguishing Job/DaemonSet-owned normal completions from ones needing review (3-11).
6. **Section 4 — Network**: node interface + inter-node ping (`oc debug node`), pod-to-pod ping (`oc rsh`), route/service external reachability (`curl`), Multus network-status annotation check.
   - If a `score-debug` namespace has a running pod labeled `app=score-debug`, item 4-2 (pod-to-pod ping) uses that pod as the *source* instead of the randomly discovered one, since it's guaranteed to have `ping` available. Items 4-3/4-4 always keep using the originally discovered namespace/pod — this separation was a previously fixed bug where swapping the whole namespace to `score-debug` broke the route check.
7. **Section 5 — Virtualization**: VM start/stop/restart and live migration (gated by `RUN_VM_DISRUPTIVE`, 5-1/5-2), VM console access (5-3, always manual/interactive — never automated), VM resource usage (5-4), DataVolume/PVC binding (5-5), NodeHealthCheck/FenceAgent status (5-6, with masked YAML detail when a FenceAgentsRemediation exists), KubeVirt/CDI component health incl. virt-handler DaemonSet worker-node coverage (5-7), per-node memory Capacity/Allocatable/Allocated (5-8), Overcommit setting (5-9), cluster-wide VM memory requests (5-10), FailedScheduling events (5-11), and a read-only audit of VM `spec.running`/`runStrategy` (5-12 — flags deprecated/misconfigured VMs but never runs `oc patch`).

## Conventions

- All section/item labels and log messages are in Korean, matching the paired xlsx checklist's item numbering — flat `<section>-<item>` (e.g. `3-1`, `4-3`, `5-12`; no more `3-1-2`-style sub-numbering, flattened 2026-09-14). Preserve this numbering exactly if adding/reordering checks, since `check_reconstructed.xlsx` and `fill_checklist.py`'s `ITEM_NUM_RE` are matched against these numbers. Adding a new item means adding both the `run_cmd` call here and the corresponding xlsx row (on rhel-prod only, see above) — never renumber existing items, only append.
- `set -uo pipefail` is used (not `-e`): individual failing `oc`/`virtctl` calls should not abort the whole run, since `run_cmd` needs to keep going and record the failure in the report for a human to review.
- Never make section 5-1/5-2/5-3 run automatically by default — they mutate or require interactive access to live VMs.
- This script must never execute a write operation against the cluster (`oc patch`/`apply`/`delete`/`scale`/`label`/`edit`) outside the explicit, gated 5-1/5-2 disruptive tests — every other item, including audits that find misconfiguration (e.g. 5-12), only reports and tells the operator what command to run manually. Verified by security review (2026-09-14): zero unguarded write calls found.
